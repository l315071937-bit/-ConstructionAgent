# 2. 项目背景

建筑工程项目在实际施工过程中，会产生大量项目资料：

- 施工图纸
- 设计说明
- 设计变更
- 会审记录
- 技术交底
- 施工组织设计
- 专项施工方案
- 工程联系单
- 材料资料
- 标准图集
- 国家标准
- 行业规范
- 地方标准
- 企业标准

这些资料通常以：

- PDF
- Word
- Excel
- 图片
- CAD 导出的 PDF
- 扫描件

等形式存在。

项目人员在实际工作中经常需要完成以下任务：

1. 从项目资料中查找具体工程信息；
2. 查询国家、行业和地方规范；
3. 查询标准图集；
4. 判断项目设计或施工做法是否符合规范；
5. 根据项目实际情况编制施工方案；
6. 根据企业内部模板编制正式工程文档。

传统方式主要依赖人工：

​```text
用户提出问题
    ↓
人工打开大量项目文件
    ↓
搜索图纸
    ↓
翻阅 PDF
    ↓
查找规范
    ↓
比对项目实际情况
    ↓
编写施工方案
```

这种方式存在：

- 查找效率低
- 文件数量巨大
- 图纸和文字资料分散
- 不同版本资料容易混淆
- 项目资料之间可能存在冲突
- 规范版本容易混淆
- 施工方案编制耗时长
- 大量重复性工作依赖人工

因此，希望建设一个面向建筑工程场景的 AI Agent 系统。

# 3. 项目核心目标

系统不是简单的：

```
ChatGPT + 知识库
```

而是构建一个：

```
项目资料
+
工程规范
+
标准图集
+
企业标准
+
AI Agent
+
人工确认
```

组成的建筑工程智能辅助系统。

核心目标：

> 让工程人员能够通过自然语言，快速查询项目资料、查询规范，并基于真实项目资料和规范辅助编制施工方案。

------

# 4. 核心业务场景

系统 V1 重点解决三个业务场景。

------

## 4.1 项目知识检索

用户可以直接询问：

```
3号楼二层卫生间防水高度是多少？

项目里消防道路采用什么做法？

A-205图纸这个位置是什么构造？

这个项目的外墙材料是什么？

项目有没有地下室防水节点？
```

系统从项目资料中检索。

核心目标：

> 回答必须尽可能基于真实项目资料，而不是依赖 LLM 自身知识。

------

# 5. 规范查询

用户可以询问：

```
深圳市政消防道路有什么规范要求？

消防车道宽度是多少？

这个施工做法符合规范吗？

这个做法对应什么标准图集？

这个规范目前是否有效？
```

系统从：

- 国家标准
- 行业标准
- 地方标准
- 标准图集
- 企业标准

中检索相关依据。

核心目标：

> 给出规范结论的同时，提供可以追溯的规范依据。

------

# 6. 施工方案智能编制

用户可以提出：

```
帮我编制地下室防水施工方案。

帮我编制消防道路施工方案。

根据这个项目资料生成主体结构施工方案。
```

系统不是直接让 LLM 凭空生成。

正确流程：

```
用户提出方案编制需求
        ↓
查询企业是否存在对应模板
        ↓
人工确认模板
        ↓
分析项目资料
        ↓
查询相关规范
        ↓
生成方案目录
        ↓
人工确认目录
        ↓
逐章节生成方案
        ↓
项目事实检查
        ↓
规范依据检查
        ↓
完整性检查
        ↓
风险检查
        ↓
人工最终审核
        ↓
生成正式文档
```

# 8. 为什么需要三个 Agent

不是为了“为了 Agent 而 Agent”。

三个 Agent 对应三个明确的业务职责：

```
项目知识检索 Agent
        ↓
项目里面到底是什么？

规范查询 Agent
        ↓
规范到底怎么规定？

施工方案 Agent
        ↓
结合项目和规范，方案应该怎么做？
```

三者形成：

```
项目事实
    +
规范依据
    ↓
施工方案
```

------

# 9. 为什么不能只使用一个 Agent

如果所有任务都放到一个 Agent：

```
一个 Agent
    ↓
项目检索
规范检索
模板检索
方案编制
文件生成
人工确认
```

会导致：

- Prompt 复杂
- State 复杂
- Graph 复杂
- 测试困难
- 错误定位困难
- 模块耦合严重

因此将业务能力拆分。

但底层能力仍然共享：

```
LLM
Embedding
Reranker
Knowledge Base
Evidence
Memory
Retry
Task
```

# 11. 为什么 Evidence 是核心

建筑工程场景属于高准确性要求场景。

例如用户问：

```
消防道路宽度是多少？
```

如果 LLM 直接回答：

```

```

用户无法知道：

```
为什么是4米？
依据什么规范？
哪个版本？
哪一条？
```

因此系统必须返回：

```
结论
+
Evidence
+
文件
+
页码
+
规范条款
```

# 16. 图纸和表格冲突

建筑项目实际资料可能出现：

```
图纸A：
尺寸 = 1800mm

图纸B：
尺寸 = 1500mm
```

或者：

```
图纸：
3000mm

Excel：
3200mm
```

系统不能简单：

```
让 LLM 自己选择一个
```

必须识别：

```
Conflict
```

然后：

```
Evidence A
+
Evidence B
+
Conflict Warning
```

必要时：

```
HITL
```

让用户确认。

------

# 17. 检索不到怎么办

系统不能：

```
检索不到
    ↓
LLM 自己编一个答案
```

正确流程：

```
第一次检索
    ↓
没有结果
    ↓
Query Rewrite
    ↓
再次检索
    ↓
仍然没有
    ↓
人工兜底
```

最终可以告诉用户：

```
当前未找到足够依据。

建议人工查看：

A-205
A-312
S-102

[打开图纸]
```

------

# 18. 三层兜底

系统统一采用：

```
第一层：
Retry

第二层：
Agent / Retrieval 降级

第三层：
Human / Manual Search
```

例如：

```
Reranker失败
    ↓
使用原始检索结果
```

或者：

```
项目检索失败
    ↓
Query Rewrite
```

最终仍然失败：

```
提示人工查看相关图纸
```

------

# 19. 人机协同原则

系统不是追求：

> AI 完全替代工程人员。

而是：

> AI 负责检索、整理、生成和检查；关键工程决策由专业人员确认。

尤其是：

```
项目资料冲突
规范适用性不确定
企业模板选择
方案目录确认
关键技术参数
高风险施工措施
最终方案
```

需要 Human-in-the-loop。

# 23. 为什么采用混合检索

建筑工程问题中存在大量：

```
图号
编号
尺寸
材料型号
规范编号
专业术语
```

这些内容非常适合 BM25。

而：

```
自然语言问题
描述性问题
相似表达
```

更适合向量检索。

所以：

```
BM25
+
Vector
```

比单独使用 Vector 更适合建筑工程场景。

# 24. LLM 的职责

```

LLM 不负责：

```

```

```
